# NOTE — M3.0 caching spike results update two PRD C9 assumptions (2026-07-19)

Measured memo: `../rk/docs/memos/2026-07-19-m3.0-caching-spike.md` (14 headless
`claude -p` calls, haiku, $0.29). The PRD required this spike before the M3.3 design
froze ("cache-hit rates must be measured in a spike before the design freezes, not
assumed" — C9); the numbers came back and two C9 assumptions are now stale:

1. **TTL**: C9 says "~5-min TTL". Measured: 1-hour default (`ephemeral_1h` populated on
   every call, `ephemeral_5m` zero). Batch-window scheduling constraints relax
   accordingly; cache writes cost 2x, so small same-prefix groups (<3 items) lose money.

2. **Dispatch shape**: M3.1's request sketch `prompt_parts {shared_prefix, item[]}`
   read as flat concatenation gets ZERO shared-block reuse — any per-item variation
   invalidates the whole prefix (measured: full cache_creation every call, 0% hit).
   Session-resume (`--resume <session_id>`, one item per turn) measured 99.6-99.8%
   cache-read per turn. The M3.1 worker contract must therefore express a
   session/turn dispatch model, not a one-shot prompt string. Role isolation is
   unchanged: a session is never reused across roles (C9 law); resume is per
   (role, batch claim).

Also confirmed: the stagger rule's premise (concurrent identical prefixes: asymmetric
hit/miss — one trial pair), and `--exclude-dynamic-system-prompt-sections` as a
campaign-wide worker setting for cross-host prefix stability.

Honest gaps (in the memo): haiku-only, claude-backend-only, no end-to-end 10-item batch,
one concurrency trial. rk bead filed for the M3.1 contract consequence.

No decision is being relitigated; this is the spike the plan itself scheduled, reported
per the CLAUDE.md stop-condition convention (surface plan-affecting findings here).
