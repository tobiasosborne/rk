# M3.2 — backend live-fire (toy end-to-end, both role directions)

Scope: the WP's own acceptance bar ("a toy proof driven end-to-end with prover=claude/
verifier=codex and the reverse"). Drives the REAL `src/drive/backend-claude.ts` /
`src/drive/backend-codex.ts` adapters' `createSession`/`runTurn` against the real `claude`/`codex`
CLIs, then `bindVerdicts` (M3.1, unchanged), on one correct lemma and one deliberately-wrong
sibling. Script lived at
`/tmp/claude-1000/-home-tobiasosborne-Projects-rk/d299c55d-9721-4240-9884-cc8d56d3b1dc/scratchpad/m3.2/livefire.ts`
(throwaway, not committed, per the M3.0 spike's own convention). 8 real subprocess calls total
(budget: ~10) — 4 per round (prover: create+1 turn or 1 turn+free create; verifier: create+2 turns
or 2 turns+free create).

## The toy artifacts

**Correct** (`lemma-a`): a 5-line statement+proof that `n + 0 = n` from the Peano base case.
**Wrong sibling** (`lemma-b`): a 5-line statement+proof CLAIMING `n + 1 = n`, whose own proof body
derives `succ(n) = n`, contradicting the stated Peano axiom `succ(n) != n` — the proof, read
honestly, refutes its own claimed statement.

## Round 1 — prover=claude (haiku), verifier=codex (gpt-5.6-sol)

| call | exit | dispatchModel | usage (input/output/cache_read/cache_creation) |
|---|---|---|---|
| prover createSession | — | — | (session-open call, no separate usage row) |
| prover runTurn (restate lemma-a) | 0 | session | 10 / 89 / 30756 / 372 |
| verifier createSession | — | flat (sends nothing) | — |
| verifier runTurn (lemma-a) | 0 | flat | 15901 / 34 / 9984 / 0 |
| verifier runTurn (lemma-b) | 0 | flat | 15927 / 42 / 15104 / 0 |

Verdicts: lemma-a -> `VALID` ("the statement is exactly the defining base equation..."), bound
cleanly by `bindVerdicts`. lemma-b -> `INVALID` ("the proof derives n + 1 = succ(n) and thus
refutes rather than proves the false statement"), also bound cleanly. **Codex correctly caught the
wrong sibling on the first try**, no re-prompting needed.

## Round 2 — prover=codex (gpt-5.6-sol), verifier=claude (haiku)

| call | exit | dispatchModel | usage (input/output/cache_read/cache_creation) |
|---|---|---|---|
| prover createSession | — | flat (sends nothing) | — |
| prover runTurn (restate lemma-a) | 0 | flat | 15782 / 22 / 9984 / 0 |
| verifier createSession | — | session | (session-open call) |
| verifier runTurn (lemma-a) | 0 | session | 10 / 328 / 30905 / 737 |
| verifier runTurn (lemma-b) | 0 | session | 10 / 469 / 31642 / 439 |

Verdicts: lemma-a -> `VALID`, lemma-b -> `INVALID`, both bound cleanly — same outcome as round 1,
confirming the verdict doesn't depend on which backend plays which role. Note claude's `input`
staying at exactly `10` on both verifier turns and `cache_read` climbing (30905 -> 31642) turn over
turn — the same "flat, small, constant `input_tokens` plus a growing cache-read total" pattern the
M3.0 spike's Finding 5 already flagged and left unexplained; still unexplained here, still
reconciling correctly (`input + cache_read + cache_creation` accounts for everything).

## contentHash stability check

Both rounds hashed the SAME lemma text (verbatim, never re-serialized) and produced the SAME
SHA-256 hex both times: lemma-a `fd49c6eb...789a5782`, lemma-b `d509f808...bd874c373` — confirms
the L5 hash domain (raw bytes, no normalization) is deterministic across independent dispatches, a
precondition M3.7's staleness check depends on.

## Real-world adapter surprises (none required a code fix — first-run clean)

1. **`codex exec` blocks on stdin unless explicitly closed**, even when a prompt is already
   supplied as a CLI argument (`codex exec --help`'s own text: "if stdin is piped and a prompt is
   also provided, stdin is appended as a `<stdin>` block" — but an *unredirected* terminal stdin
   just hangs waiting for EOF). `backend-codex.ts` passes `input: ""` on every `runTurn` call
   specifically because of this — confirmed necessary during manual CLI probing before the adapter
   was written (a bare `codex exec "prompt" --json` without `</dev/null` printed "Reading
   additional input from stdin..." and hung).
2. **ChatGPT-account codex rejects several plausible "cheap" model ids** (`gpt-5.1-codex-mini`,
   `gpt-5-mini` both returned HTTP 400 "not supported when using Codex with a ChatGPT account")
   even though `codex exec` accepts `-m <anything>` syntactically and only fails at the API call.
   The account's configured default (`~/.codex/config.toml`: `model = "gpt-5.6-sol"`) works when
   passed explicitly, and self-reports (unreliably — see below) as `gpt-5-codex` under one probe.
   This WP's registry treats `model` as an opaque per-repo config value the driver supplies, never
   a value the adapter validates or guesses.
3. **Never trust self-reported model identity** (this was already a design principle, not a
   surprise, but the live-fire reconfirms it concretely): asking the live codex process "what model
   are you?" returned `gpt-5-codex`, while the account's own config names `gpt-5.6-sol` as the
   configured default — an inconsistency between what the backend will SAY and what it is actually
   CONFIGURED to run as. `modelFamily`/`model` in this WP's adapters come from the caller-supplied
   `SessionSpec.model`, never from anything printed by the process, exactly per docs/
   worker-contract.md section (e) — this data point is a concrete argument FOR that rule, not
   merely a hypothetical one.
4. **Claude's `usage.input_tokens` is a small near-constant (`10` in every successful call in this
   live-fire, matching the M3.0 spike's own Finding 5 oddity) regardless of prompt size** — still
   unexplained, still reconciles correctly against the total. Recorded again here as a second,
   independent confirmation (different day, different corpus) of the same M3.0 observation.
5. **`codex exec`'s `turn.completed` usage event has no cache-WRITE figure** (only
   `cached_input_tokens`, the read side) — `backend-codex.ts` reports `cache_creation: 0` for every
   codex call, honestly "not exposed by this CLI," never a guessed nonzero value. This means a
   token-accounting report (M3.9) reading codex-authored turns will always show a zero write figure
   for that backend, which is a REPORTING gap, not evidence that codex performs no caching
   internally.
6. **`codex exec resume <thread-id>` exists as a real subcommand** (confirmed via `codex exec
   --help`'s `Commands: resume`) — the CLI plumbing a future codex-session spike would exercise is
   already present; this live-fire did not touch it (out of scope per the Q1 ruling, which requires
   a DEDICATED spike, not incidental discovery, before `dispatchModel` could change for codex).

## What a future codex-session spike (Q1) would need to measure

Per docs/worker-contract.md's still-open item ("Codex defaults to `dispatchModel:'flat'` until a
Codex-specific spike proves continuation semantics"): (a) whether `codex exec resume <thread-id>`
actually re-sends shared context or genuinely continues a server-side conversation state (the
`thread_id` this live-fire's JSONL stream already surfaces on every call, unused here); (b) whether
resumed-turn `usage` shows a cache-read-dominated pattern analogous to claude's session-resume
Finding 2, or whether ChatGPT-account codex caching behaves differently from API-key codex; (c)
whether `-m`/model selection persists correctly across a resume call the way claude's does. None of
this was measured here — this live-fire deliberately stayed inside the Q1 ruling's flat-dispatch
default for codex throughout both rounds.
