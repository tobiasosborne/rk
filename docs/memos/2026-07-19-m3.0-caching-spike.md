# M3.0 — caching measurement spike

Scope: headless `claude -p` prompt-caching behavior, measured directly against Anthropic's API
through the CLI — NOT run against AISM or the dogfood repo (CLAUDE.md rule 3 / spike brief
constraint). All calls executed from `/home/tobiasosborne/Projects/rk` (this repo, `CLAUDE.md`
present and auto-loaded). Throwaway scripts and raw JSON output live in
`/tmp/claude-1000/-home-tobiasosborne-Projects-rk/d299c55d-9721-4240-9884-cc8d56d3b1dc/scratchpad/m3.0/`
(not committed, per the spike brief).

**Environment**: Claude Code CLI `2.1.215`. Model `claude-haiku-4-5-20251001` (`--model haiku`)
throughout — cache mechanics are prefix-byte-matching and TTL/pricing-tier behavior, not
model-capability-dependent, so a small model was used per the budget constraint; this was not
separately re-verified on Sonnet/Opus (see Honest gaps). Flags used: `--output-format json`
(machine-readable `usage` block), `--no-session-persistence` for one-shot calls,
`--resume <session_id>` for multi-turn calls, one comparison call with
`--exclude-dynamic-system-prompt-sections`. No custom `--system-prompt`, no `--tools` override,
default tool set and default hooks/CLAUDE.md loading throughout (i.e. exactly what a real rk
worker invocation would inherit unless the driver opts out).

Corpus used as the "shared context" block: `../research-workflows/IMPLEMENTATION_PLAN.md` +
`../research-workflows/PRD.md`, concatenated verbatim (8,377 words / 58,657 bytes; renders to
~19,372–23,554 tokens depending on what else is already warm in the same breakpoint — see
below). This sits inside the plan's 8–15k-token target once the CLI's own fixed prefix is netted
out, and is large enough to dominate a batch item's own content.

Total spike cost: 14 `claude -p` calls, **$0.287**, ~549k cumulative tokens across all
usage categories (dominated by repeated reads/writes of the same ~41k-token warm prefix).

## Headline numbers

| scenario | cache-read fraction (of total tokens processed that call) | note |
|---|---|---|
| Flat string, first call in a burst (cold-ish) | ~42% | reads only the CLI's own prior warm prefix; nothing of the shared corpus was cached yet |
| Flat string, steady state (calls 2–4), **suffix varies 1 char each call** | **0%** on the shared-corpus portion; ~53% blended (only the CLI's own fixed prefix hits) | the shared corpus (~19,372 tokens) is rewritten from scratch on **every** call — see Finding 1 |
| Flat string, **byte-identical** repeat (same suffix) | **~99.98%** | confirms caching works fine when the whole rendered prompt is unchanged |
| Session-resume, turn 1 | ~100% (already warm from the identical-repeat trial) | first turn pays the write in the cold case |
| Session-resume, turns 2–4 (new item each turn, no shared-context repeat) | **~99.6–99.8%**, ~82–174 new tokens/turn | this is the pattern M3.3 needs to adopt — see Recommendation 1 |
| Session-resume after a 180s gap | ~99.8% | TTL held; see Finding 3 |
| Concurrent identical-prefix pair (one trial) | one call ~100%, the other ~53% | asymmetric, not "both hit" — see Finding 4 |

## Method

Four scenarios, in order, all on the same warm shared-corpus prefix once established:

1. **Sequential flat-string calls** (`call_1.json`–`call_4.json`): one `claude -p` invocation per
   call, prompt = shared corpus + a one-character-varying arithmetic suffix ("reply with the
   number result of 2+N"), `--no-session-persistence` (fresh process, fresh conversation, no
   resume) so each call is a genuinely independent request the way a naive batch dispatcher
   might build one.
2. **Byte-identical repeat** (`call_5.json`, `call_6.json`): same flat-string shape, but the
   suffix is held fixed across both calls — isolates whether caching works at all for this
   corpus size when nothing downstream of the CLI's own prefix differs.
3. **Session-resume / turn-based** (`turnA.json`–`turnD.json`): one `claude -p` call *without*
   `--no-session-persistence` to establish a session and capture its `session_id`, then three
   more calls via `--resume <session_id>`, each sending **only** the new item (no shared-corpus
   repetition) — the pattern a persistent per-role worker session would actually use. `turnD`
   is issued after a 180s sleep to get one TTL data point.
4. **Concurrency** (`conc_A.json`, `conc_B.json`): two `claude -p` processes launched
   back-to-back in the same shell (`cmd &`, `cmd &`, `wait`) with a byte-identical, previously
   never-used prompt (fresh timestamp+pid marker embedded in the shared corpus so neither call
   could ride on an already-warm entry), to see whether both miss or the outcome is asymmetric.

`usage.cache_creation_input_tokens`, `usage.cache_read_input_tokens`, `usage.input_tokens`, and
the `cache_creation.ephemeral_1h_input_tokens` / `ephemeral_5m_input_tokens` split were read
straight off the CLI's `--output-format json` result object — no parsing ambiguity; the JSON
shape is stable and matches the API's `usage` block field names.

## Finding 1 — flat-string concatenation gets ZERO cache benefit on the shared block once the suffix varies

This is the central, load-bearing result. Concatenating `shared_prefix + item` into a single
prompt string (the naive reading of `prompt_parts {shared_prefix, item[]}` from the PRD) does
**not** give per-item cache reuse, because the `claude -p` CLI exposes no way to insert an
intermediate `cache_control` breakpoint between the two parts. The entire rendered user turn —
shared corpus and the trailing item text together — is one contiguous block from the cache's
point of view. Per `shared/prompt-caching.md`'s prefix-match invariant, a single differing byte
anywhere invalidates cache-read for everything after the last real breakpoint; our trailing
one-character suffix sits *inside* that block, so it invalidates the whole ~19,372-token shared
corpus every time:

| call | suffix | cache_read | cache_creation | total | shared-corpus hit? |
|---|---|---:|---:|---:|---|
| 1 | `2+1` | 17,418 | 23,554 | 40,982 | no (cold burst-start) |
| 2 | `2+2` | 21,600 | 19,372 | 40,982 | **no** |
| 3 | `2+3` | 21,600 | 19,372 | 40,982 | **no** |
| 4 | `2+4` | 21,600 | 19,372 | 40,982 | **no** |
| 5 | `2+1` (repeat of call 1) | 40,972 | 0 | 40,972 | **yes — full hit** |
| 6 | `2+1` (repeat) | 40,972 | 0 | 40,972 | **yes — full hit** |

Calls 2–4 show a perfectly flat 19,372-token `cache_creation` every single time — the shared
corpus is rewritten from scratch, paying the 1.25×/2× write premium, on every call, forever,
under this prompt-assembly pattern. Calls 5–6 (identical full prompt, suffix included) confirm
this isn't a corpus-size or model-tier problem: when nothing downstream differs, the entire
~41k-token prefix hits at ~99.98%, cache_creation drops to 0, and cost drops roughly 9× (see raw
files `call_5.json`, `call_6.json`).

**Conclusion: `rk verify`'s worker dispatch must not build one flat prompt string per item.** If
it does, M3.4's "shared-context preference" batch composer buys nothing — the whole point of
grouping sibling leaves under one shared subtree context is defeated by the CLI's flat-string
assembly.

## Finding 2 — session-resume (turn-based dispatch) is the actual cache-safe mechanism

Re-running the same shared corpus through `--resume <session_id>`, sending each new item as a
*new turn* instead of re-concatenating the corpus, gets the cache behavior the PRD assumed:

| turn | new content sent | cache_read | cache_creation | total | new-content fraction |
|---|---|---:|---:|---:|---|
| A (fresh session, corpus + item 1) | full corpus + item | 40,972 | 0 | 40,982 | 0% (was already warm from calls 5–6) |
| B (resume, item 2 only) | ~15–20 tokens of new text | 40,972 | 174 | 41,146 | 0.4% |
| C (resume, item 3 only) | ~15–20 tokens | 41,146 | 82 | 41,228 | 0.2% |
| D (resume, item 4, after 180s gap) | ~15–20 tokens | 41,228 | 82 | 41,310 | 0.2% |

Each new turn pays only its own small delta (82–174 tokens, essentially the new user-turn text
plus whatever bookkeeping the CLI attaches per turn); everything from prior turns — including
the entire shared corpus — is served from cache. This is the mechanism that actually realizes
the batching cost model in PRD C3 (`C_shared + Σ(c_i + v)`): the shared context is paid for once
(turn 1), and each subsequent item pays close to nothing extra for context, only its own
processing.

## Finding 3 — TTL: 1-hour, not 5-minute, and it held across the one gap tested

**Correction to the PRD's stated assumption.** PRD C9 says "Anthropic caching is byte-exact
prefix matching across separate requests (~5-min TTL)". Every one of the 14 calls in this spike
— all of them, with no exception — reported its cache activity entirely under
`cache_creation.ephemeral_1h_input_tokens`, and `ephemeral_5m_input_tokens` was 0 in every
single response. The Claude Code CLI defaults to the 1-hour cache tier, not the 5-minute
default the bare Messages API uses. This is favorable for M3.3: it means the per-item
verification gap (the plan's "~2–4 min" concern) is nowhere near the actual expiry window.
`turnD` (180s / 3 minutes after `turnC`) still hit at 41,228/41,310 ≈ 99.8% — the single
confirming data point the plan asked for, and it landed well inside a 1-hour window so it
proves less about the boundary than a 55-minute gap would, but it does confirm the assumed
5-minute TTL was already a non-issue for this cadence, and the actual TTL is far more forgiving
than assumed.

**Practical implication**: the 1-hour tier costs 2× to write (vs 1.25× for 5-minute), so the
break-even point for a shared-context group shifts — see Recommendation 3.

## Finding 4 — concurrent identical-prefix dispatch is asymmetric, not a clean "both miss"

Two `claude -p` processes launched back-to-back (`&`, `&`, `wait`) with a byte-identical,
never-before-seen prompt:

| call | cache_read | cache_creation | total | outcome |
|---|---:|---:|---:|---|
| `conc_A` | 40,995 | 0 | 41,005 | full hit — won whatever race determined write order |
| `conc_B` | 21,600 | 19,395 | 41,005 | full miss on the shared-corpus portion — paid the full write |

The documented rule ("N parallel requests with identical prefixes all pay full price — none can
read what the others are still writing") describes the worst case; what we actually observed
with ordinary shell-level concurrency (not synchronized to the same instant at the network
layer) was one caller winning a race it had no way to guarantee, and the other paying full
price. The practically important part is the same either way: **you cannot rely on concurrent
dispatch to give every caller the cached price.** At least one of any concurrent pair eats a
full, redundant write. This is exactly the failure mode the PRD's stagger rule exists to
prevent — confirmed, not merely assumed.

## Finding 5 — prefix stability ahead of rk's own prompt, and what breaks it

The CLI's own system-prompt + tool-definitions + CLAUDE.md + directory/environment-info block
**is** byte-stable and cacheable across completely separate `claude -p` process invocations —
this part of the "ahead of our prompt" content behaved exactly as hoped, growing from a 17,418
baseline toward a stable ~21,600-token plateau across the burst of calls in this session and
persisting across all later scenarios without ever needing a full rewrite once warm.

What breaks it:

1. **No mid-message breakpoint is exposed.** Everything the caller passes as the prompt argument
   is rendered as one user-turn block after the CLI's own fixed prefix. There is no CLI flag to
   mark "this part is stable, this part varies" within a single flat call (Finding 1).
2. **`--exclude-dynamic-system-prompt-sections` changes the cache key.** A same-corpus,
   otherwise-identical tiny call with this flag added produced `cache_creation: 4337`,
   `cache_read: 20350` (total 24,697) instead of the ~30,929-token baseline the same tiny prompt
   produced without the flag — a different, smaller structure, because cwd/env/git-status
   content moved out of the system prompt and into the first user message. Turning this flag on
   or off between calls is itself a cache-invalidating change; it must be a fixed, repo-wide
   worker setting, never toggled per-call.
3. **Any per-machine content baked into the system prompt** (cwd, env info, git status) will
   differ across hosts. A campaign running verification workers on multiple machines/CI runners
   risks the "ahead of prompt" prefix itself varying host-to-host, breaking cross-worker cache
   sharing even when the shared corpus is identical. `--exclude-dynamic-system-prompt-sections`
   exists specifically to move that content out of the system prompt for this reason — see
   Recommendation 4.
4. **Model, tool set, and `--resume`/session identity are all cache-partition boundaries** per
   the API's own invalidation hierarchy (`shared/prompt-caching.md`'s table) — switching model,
   adding/removing a tool, or resuming the wrong session all force a fresh write. Not separately
   re-verified in this spike (see Honest gaps) but is documented API behavior, not a CLI-specific
   finding, and is already reflected in the PRD's "never resume a session across roles" rule.

An oddity worth recording honestly rather than explaining away: `usage.input_tokens` was
reported as exactly `10` in every one of the 14 calls in this spike, regardless of prompt size
(the 8,377-word corpus and the one-word "Say OK" characterization call alike). Total tokens
processed reconcile correctly as `input_tokens + cache_creation_input_tokens +
cache_read_input_tokens` in every case, so this isn't a missing-data problem — it appears the
CLI buckets nearly everything the caller supplies into a cacheable block by default, leaving a
small, constant, always-uncached remainder (plausibly a per-request wrapper/metadata token) as
`input_tokens`. Not fully explained; flagged for whoever next reads a `usage` block from this
CLI and finds the same constant.

## Honest gaps — not measured, and why

- **Only Haiku 4.5 was used.** Cache mechanics (prefix-byte-matching, TTL, price multipliers)
  are documented as backend-tier behavior, not model-capability behavior, so this is expected to
  generalize to Sonnet/Opus — but it was not separately re-run on either, per the spike's budget
  cap (~15–25 calls; this spike used 14).
- **Only the `claude` backend was measured.** The `codex exec` backend (also named in PRD D8 /
  M3.2) has its own, documented-as-automatic-and-opaque caching with smaller discounts; this
  spike does not touch it — M3.0's brief scoped the spike to the headless `claude -p` CLI only.
- **A real 10-item batch was not run end-to-end.** Budget-consciousness (the brief's explicit
  instruction) capped this spike at 4-turn session-resume chains, not 10. The per-turn marginal
  cost (Finding 2: 82–174 tokens/turn) is linear and small relative to the ~41k-token shared
  corpus, so extrapolation to 10 turns is a straight-line estimate, not a separately measured
  number — M3.3's own acceptance run (against a real 10-item batch) is what closes this gap, and
  should re-confirm the derived target below rather than assume it holds unchanged.
- **The 1-hour TTL's actual boundary was not probed.** One gap of 180 seconds was tested per the
  plan's "one confirming data point suffices" instruction; a gap approaching the full hour
  (needed to find where cache reads actually start missing) was out of scope for a
  budget-conscious spike and is not needed for M3.3's cadence (per-item gaps of 2–4 minutes are
  nowhere near either the 5-minute or 1-hour boundary).
- **Only one concurrency trial pair was run**, per the plan's explicit "one trial pair
  suffices." The asymmetric-not-symmetric outcome observed (Finding 4) is a single data point;
  it is presented as evidence against relying on concurrent dispatch, not as a precise measurement
  of win/loss probability.
- **Tool definitions were left at CLI defaults** (not disabled via `--tools ""`) throughout, to
  keep the measured prefix representative of what a real worker invocation inherits. This means
  the reported ~21,600-token "ahead of prompt" baseline includes tool schemas; a worker role that
  disables tools entirely (e.g. a pure-text L5 verifier) would see a smaller, more stable fixed
  prefix — not separately measured here.

## Recommendations for M3.3 (derived from the above)

1. **Session-resume, not flat-string concatenation, is the required dispatch mechanism.**
   `rk verify`'s session/cache manager must open one persistent `claude -p` session per
   (role, shared-context group) — created once *without* `--no-session-persistence`, with the
   returned `session_id` retained by the driver — and dispatch each batch item as a
   `--resume <session_id>` call carrying only that item's own content, never re-sending the
   shared corpus. This is not an optimization on top of the PRD's design; it is the only pattern
   in this spike that gave the shared corpus any cache benefit at all (Finding 1 vs Finding 2).
2. **Cache-read fraction target for a 10-item batch: ~85–90% by token count, with per-turn
   (turns 2–10) individually at ≥95%.** Derived, not measured directly (see Honest gaps): turn 1
   of any group necessarily pays the full write (0% hit by construction); turns 2–10 each hit at
   the observed ~99.6–99.8% steady-state rate. A token-weighted average across a 10-turn group
   works out to roughly 9×0.997⁄10 ≈ 90%, dragged down only by the unavoidable first turn. If
   M3.3's live acceptance run measures materially below ~85% on turns 2+, that is a regression
   signal (something is breaking prefix stability per Finding 5), not an acceptable outcome to
   average away.
3. **The stagger rule is confirmed necessary, not merely assumed.** Finding 4 shows concurrent
   identical-prefix dispatch is asymmetric — one caller can win a race, but at least one is
   guaranteed to pay the full uncached write. The batch composer must dispatch the first call of
   every same-prefix group alone, await its first streamed token, then fire the rest — exactly
   the PRD's stated design, now backed by a direct trial rather than the documented worst case
   alone.
4. **Pass `--exclude-dynamic-system-prompt-sections` on every worker invocation, fixed for the
   life of the campaign.** It measurably shrinks and stabilizes the CLI's own fixed prefix
   (Finding 5, item 2) by moving per-machine content (cwd, env, git status) out of the
   system-prompt cache key — important if verification workers ever run across more than one
   host or CI runner within a campaign. Toggling this flag mid-campaign is itself a
   cache-invalidating, one-time-cost event; pick it once at `rk init`/`.rk/config` time.
5. **Shared-context group size floor: ≥3 items, given the observed 1-hour default TTL.** Finding
   3's TTL correction changes the batching economics stated in `shared/prompt-caching.md`: a
   5-minute-TTL write breaks even at 2 requests, but a 1-hour-TTL write (which is what this CLI
   actually uses, unconditionally, in every call observed) needs ≥3 requests sharing the same
   context to come out cheaper than never caching at all. M3.4's batch composer already defaults
   to a cap of 10 and prefers grouping sibling leaves of one subtree — this recommendation adds a
   **floor**: a shared-context group of only 1–2 items should not be treated as a caching win,
   even though the per-token cache-read price looks like a good deal in isolation.
6. **Minimum shared-prefix size**: below ~4,096 tokens (Haiku 4.5/Opus-tier's documented minimum
   cacheable prefix, per `shared/prompt-caching.md`), caching silently does not activate at all —
   no error, `cache_creation_input_tokens: 0`. rk's real shared contexts (conjecture + common
   ancestors + definitions for a subtree) are expected to exceed this easily in practice, but
   M3.3 should treat "shared context under ~4k tokens" as a case where caching is not worth
   engineering around — batch on independence/critical-path grounds only, not on
   shared-context grounds, below that size.
7. **Never build the worker prompt as `shared_prefix + item` concatenated into one string, even
   inside a single session-resume turn.** Recommendation 1 already rules this out across turns;
   it also matters within the very first turn of a new session (Finding 1, call 1's 23,554-token
   cache_creation) — the first turn of any group is an unavoidable full write regardless of
   internal structure, so this point is about turns 2+ only: keep each subsequent turn's content
   to just the new item, nothing repeated from the shared corpus.
