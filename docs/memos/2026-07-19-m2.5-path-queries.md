## Critical-path semantics (the exact rule, and why it is safe for M3.4)

**Rule:** a node is on the critical path to north star `S` iff it is `S` itself, or it is named —
directly or transitively — as an AND-dep OR an OR-route member of some node already on the path.
**Both branches of every OR-route count**, not only whichever route currently happens to be
satisfied.

**Why this is the right call, not just a convenient one:** PRD §4 C2 requires the critical-path
provenance check to run "continuously ... because path membership changes when edges are added,
not only at verdict-apply time." A route unsatisfied today can become the satisfied route
tomorrow with no signal to the batch composer other than re-running this query. The two failure
directions are asymmetric:
- Falsely **excluding** a node that turns out load-bearing lets it be verified in a batch — the
  exact validity-barrier violation PRD §4 C3's critical-path-exclusion guardrail exists to
  prevent.
- Falsely **including** a node that turns out never load-bearing costs one batching opportunity —
  a node gets per-node treatment it strictly didn't need.

Given that asymmetry, `computeCriticalPath` always resolves ambiguity toward inclusion. A node is
excluded ONLY when it is not reachable via ANY combination of deps/route edges from the north
star at all. `computeCriticalPath`'s own module doc comment states this rule in full, so a future
reader touching the file sees the reasoning before touching the code.

**M3.4 consumer contract:** `CriticalPathResult.nodeIds` is a sorted array, north star included;
M3.4 is expected to build `new Set(result.nodeIds)` once per composer run and query membership
per candidate — `computeCriticalPath` itself is meant to run once per composer invocation, not
once per candidate.

Referential robustness: the traversal walks through phantom ids (a dep naming no real node) so
reachability THROUGH one is not lost, but the reported `nodeIds` only ever names real document
nodes (an unresolved reference is `doc.unresolved`'s job to surface, not this query's to invent a
node for). A cycle (which Gate 2's `checkAcyclic` should already reject, but a pure query must not
assume) is cycle-safe via a `seen` guard in `closureFrom` — never an infinite loop.

## Taint trace semantics

`computeTaintTrace` transplants ../vibefeld's own `af taint-trace` priority order (`cmd/af/
taint_trace.go`'s `taintReason`; `docs/concepts.md` "Taint States") onto the registry requirement
graph: af's "ancestor" (closer to the proof root) is this graph's "requirement" (a node's deps +
route members) — X depends on Y means Y is X's foundation, exactly the role af's "ancestor" plays
for one workspace's internal tree. Priority order, highest first: (1) own taint is `unresolved` →
unresolved, self-caused; (2) any requirement is `unresolved` → unresolved, propagated; (3) own
taint is `self_admitted`/`tainted` → that value, self-caused; (4) any requirement is `tainted`/
`self_admitted` → `tainted`, propagated; (5) otherwise `clean`. Same over-inclusion stance as the
critical path: every OR-route member contributes, not only the satisfied route. A node with
`af: "none"` contributes no taint of its own but still propagates any taint reachable through its
own deps/routes — campaign-wide taint is about the whole registry closure, not only the
af-tracked subset.

## "What blocks" semantics

`computeWhatBlocks` splits the critical path's not-yet-available nodes into `frontier` (own
prerequisites — deps + at least one route — already met, i.e. actionable right now, the fr
"wavefront" sense) and `blocked` (own prerequisites not yet met either). Each entry carries
structured `reasons` (status/af mismatch, unmet dep ids, no route satisfied).

## North-star identification: decision (Tier A — flagged for review)

**Decision:** an optional validated `.rk/config.json` field, `GateConfig.northStarId?: string`,
mirroring the already-reviewed `shardsPrefix` pattern exactly: no default (a general tool must
never guess a campaign's north star), a present-but-malformed value produces one loud
`structural: true` config ERROR and is dropped (never a silent guess), and an explicit
`--north-star <id>` CLI flag always overrides the config value when both are given.

**Diff, in full** (`src/gates/config.ts`):
- `GateConfig.northStarId?: string` added, doc comment cross-referencing `src/cli/graph.ts`.
- `"northStarId"` added to `KNOWN_CONFIG_KEYS` (so it is never flagged as an unrecognized key).
- One new `if ("northStarId" in raw)` validation block in `validateConfigOverrides`, identical
  shape to the existing `shardsPrefix` block (`isNonEmptyString`, one `configError` finding on a
  malformed value, dropped from `overrides` either way).

No change to `src/store/config-load.ts` (its `loadGateConfig`/`mergeGateConfig` composition is
already field-agnostic) and no change to `configGate` (it already surfaces whatever
`validateConfigOverrides` finds, per-field-agnostic). Two new unit tests in
`test/gates/config.test.ts` (`northStarId (M2.5): a non-empty string passes through`,
`northStarId: malformed (non-string / empty) value rejected`) mirror the existing `shardsPrefix`
coverage exactly. No new `corpus/config/` fixture was added — `shardsPrefix`, the field this one
mirrors, also has no dedicated corpus fixture (only `test/gates/config.test.ts` unit coverage);
this WP follows that same precedent rather than introducing a new one.

This is genuinely small (three touch points, one pre-reviewed pattern reused verbatim) but is
still a `src/gates/` change to a Tier A file (config validity is validity semantics, CLAUDE.md
L6) — flagged here explicitly per this WP's brief, for the milestone-boundary review to look at
directly rather than trusting the implementer's own characterization.

campaign, same binaries the M2.2 read-through memo used) via a throwaway script, deleted after
use — not committed, per the M2.2 memo's own precedent (the rename-hazard corpus fixture is the
