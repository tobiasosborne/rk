## 6. Verdict-parity check procedure

The claim to check: the fresh re-proof reaches the SAME validity outcome as AISM's original
validation, node-for-node in spirit (a fresh tree need not have the same node ids/shape — the
prover may decompose differently — but the ROOT conjecture's final disposition and any raised-then-
resolved challenges should be comparable in kind).

Per lemma, after a live run completes:

1. **Root disposition.** Fresh workspace: read the final `proofs/<id>/export.md`'s Node 1 `Status`
   and `Taint`. Compare against the original AISM workspace's Node 1 (`proofs/<id>/export.md` in
   AISM, read-only) — both should show `Status: validated`, `Taint: clean`. A fresh `INVALID` or a
   taint that never clears is the interesting case, not a shrug: it means the current protocol
   found something AISM's original run did not (or the reverse — a real red-corpus candidate).
2. **Ledger event-type histogram.** For each workspace, count ledger events by `"type"` field
   (`proof_initialized`, `node_created`, `node_validated`, `challenge_raised`,
   `challenge_resolved`, `nodes_claimed`, `nodes_released`, `claim`, `def_added`). Compare COUNTS of
   `challenge_raised`/`challenge_resolved` between fresh and original — a materially different
   challenge rate (e.g. fresh run raises zero challenges where the original had one, or vice versa)
   is itself SC4-adjacent signal about protocol rigor, not just cost, and belongs in the parity
   table's notes column, not silently dropped.
3. **Node count.** Compare fresh `nodeCount` (from `rk verify --af <id> --dry-run`'s output, or the
   final `export.md`) against the original's node count from this memo's §2 table. A large
   divergence (especially exceeding `DEFAULT_BALLOON_NODE_CAP` = 40,
   `src/drive/driver-balloon.ts`) is a balloon, handled per §7, not silently absorbed into "parity."
4. **Reviewer != author.** Confirm the fresh run's verifier identity differs from the prover
   identity for every accepted node (the same rule `docs/verdicts-apply.md` states for af's batch
   path; here it is per-node since hard tier is never batched) — this is mechanically true by
   construction under the worker contract's session isolation (`src/drive/session.ts`), but the
   parity check should still assert it explicitly against the driver log's recorded `verifier`/
   prover session records, not assume it silently.

## 7. Abort criteria (stop and report — never grind past these)

Per CLAUDE.md Rule 11 ("estimates are tripwires") and the M3.6 guardrail vocabulary already
implemented and unit-tested in `src/drive/driver-guardrails.ts` / `driver-balloon.ts`:

- **Balloon tripwire**: live node count exceeds `DEFAULT_BALLOON_NODE_CAP` = 40. For these three
  lemmas (7-9 original nodes), ANY fresh re-proof exceeding roughly 3-4x the original node count
  (i.e. >25-35 nodes, well before the hard 40 cap) should be treated as a yellow flag worth manually
  checking before it trips the hard cap — a fresh decomposition materially bushier than the
  original, on a lemma this small, is more likely a mis-run than genuine new difficulty.
- **Stuck guard**: `DEFAULT_MAX_STUCK_ROUNDS` = 3 consecutive dispatch rounds with zero applied
  verdicts aborts the claim (`evaluateStuckGuard`, `src/drive/driver-guardrails.ts`) — already
  wired into the driver loop; nothing extra for the session to configure.
- **Retry/churn cap**: `DEFAULT_NODE_RETRY_CAP` = 3 attempts per node
  (`checkRetryCap`, same file) — same, already wired.
- **Prover-overreach abort**: a prover turn structurally carrying a `verdict`/`outcome` field is
  discarded automatically (`detectProverOverreach`) — a session should note if this fires even
  once; it means a backend or prompt-assembly bug let a prover attempt to self-certify.
- **Cost ceiling per lemma — a JUDGMENT CALL, not yet an empirically-derived number** (this session
  IS the first real measurement; no prior rk token/call number exists to derive one from). Proposed
  circuit-breaker: **budget.maxTotalTokens per node dispatch set generously (the worker-contract's
  `budget` field, `docs/worker-contract.md` §(b)) and a campaign-level stop if total spend across a
  single lemma's re-proof exceeds roughly 50x the M3.0 spike's single-call token count
  (`../research-workflows/NOTES-2026-07-19-m3.0-caching-spike.md`) without reaching a validated
  root** — i.e., if the SIMPLEST of these three lemmas (8-9 original nodes) is burning tokens at a
  rate that would need 50+ single-call-equivalents to finish, something is wrong (a churn loop, a
  prompt-assembly bug, or a genuine balloon) well before it becomes an expensive surprise. Revise
  this number once real M3.5 data exists — it is deliberately conservative and explicitly a guess,
  never presented as measured.
- **Any abort must be reported, never silently retried past its cap** — consistent with CLAUDE.md
  L2 ("a silent skip is a bug") applied to cost/progress guards, not just gate coverage.

## 8. Memo-output contract (what the live session must produce)

**Baseline memo** (M3.9's `--baseline` input, `src/drive/report.ts:216-217`):

```ts
export interface BaselineEntry { lemma: string; tokens: number; calls: number; }
export type BaselineMemo = BaselineEntry[];
```

validated by `parseBaselineMemo` (same file) — a plain JSON array, each entry `{lemma: string,
tokens: number, calls: number}`, nothing else (unknown/missing fields reject the whole entry's
parse, per that function's `isPlainObject(entry) && isNonBlankString(entry.lemma) &&
isNumber(entry.tokens) && isNumber(entry.calls)` check).

**Load-bearing subtlety for whoever runs the live session** (found by reading, not assumed):
`compareToBaseline` (`src/drive/report.ts:247-256`) matches `baseline.lemma` against a
**CampaignReport's per-node `nodeId`**, not a top-level lemma registry id — `report.nodeRows.find((n)
=> n.nodeId === b.lemma)`. Since each of these three scratch dirs is its OWN campaign root (its own
`.rk/driver-log.jsonl`, its own af workspace with LOCAL node ids like `1`, `1.1`, `1.1.1`, ...), a
baseline memo scoped to one lemma's fresh re-proof must key its entries by THAT WORKSPACE'S OWN af
node ids, not by the registry id `lem-weighted-min` etc. — and `rk verify --report --baseline
<memo> --root <that-lemma-dir>` must be invoked separately, per lemma, against a memo scoped to that
lemma's own node-id namespace (node ids collide across workspaces — `1` means something different
in every one of the three scratch dirs). Concretely, expect three small baseline memos (one per
lemma dir), each shaped like:

```json
[
  {"lemma": "1", "tokens": 1234, "calls": 3},
  {"lemma": "1.1", "tokens": 890, "calls": 2}
]
```

not one combined array using registry ids as the key — that would silently mismatch against
`nodeRows` and produce `ratio: undefined` for every row (the function's own honest-miss behavior,
per its doc comment: "never fabricates a denominator"). If a single combined cross-lemma memo is
wanted for the M3.5 WP report, it should be assembled by RUNNING `--report --baseline` three times
(once per lemma root) and concatenating the resulting comparison rows in the parity table above —
not by trying to feed one memo to one `--report` call across three campaign roots (the CLI has no
multi-root mode).

report-scaffold-required mode, which then ERRORs on missing `report/main.tex`, `report/sections/`,
`report/README.md`, `report/SHARD_CATALOG.md` — i.e., whitelisting the anchor check trades one

scratch dirs** for this reason — the config-only ERROR-free state (§9's clean 3/3, before any
`report/` dir existed) is what ships. This is worth flagging to whoever eventually wires
`rk check` into any single-lemma scratch/dogfood flow: **the anchor check and the shards gate
disagree about what "off paper-track" should cost you**, and a scratch dir like this one currently
has no clean way to satisfy both simultaneously short of building a full (if minimal) report
scaffold. Not fixed here — flagging per CLAUDE.md's stop-condition norm ("a PRD/plan conflict or
gap discovered mid-WP" — this is closer to a gate-interaction gap than a PRD conflict, but the same
"surface it, do not silently route around it" discipline applies) rather than silently working
around it with a fabricated report scaffold that would misrepresent these dirs as paper-anchored.
