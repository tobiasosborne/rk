## LANDING-BLOCKERS

1. **MAJOR — Readiness is staleable across both mutation and acceptance, and af does not re-enforce the dispatched role.** rk takes one snapshot, dispatches, and records a prover result without re-reading either the content hash or `prover_ready` ([driver-run.ts:93](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:93), [driver-run.ts:132](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:132)). The live seam then claims and refines using that stale result ([driver-af.ts:142](/home/tobiasosborne/Projects/rk/src/drive/driver-af.ts:142)). In af, `--role prover` is validated only by the CLI, then discarded when calling the role-agnostic `ClaimNode` ([claim.go:90](/home/tobiasosborne/Projects/vibefeld/cmd/af/claim.go:90), [claim.go:109](/home/tobiasosborne/Projects/vibefeld/cmd/af/claim.go:109)); `ClaimNode` checks only that the node is currently available ([proof.go:465](/home/tobiasosborne/Projects/vibefeld/internal/service/proof.go:465)). Thus an amendment or challenge resolution during the model turn can attach a proof generated for old bytes or to a node no longer classified for prover work.

   The verifier half re-reads only the node’s own content hash ([driver-run.ts:161](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:161)); af acceptance rechecks challenges, children and epistemic transition, but not `workflow_state === available` or current `verifier_ready` ([proof.go:829](/home/tobiasosborne/Projects/vibefeld/internal/service/proof.go:829), [proof.go:897](/home/tobiasosborne/Projects/vibefeld/internal/service/proof.go:897)). A node becoming claimed or blocked without changing its content hash can therefore still be accepted from a stale verifier snapshot—a wrong apply, not merely wasted spend.

   **Fix:** make readiness enforcement atomic in af. Prover claim/refine must carry and check the expected content hash and current prover-job classification; `verdicts apply` must check expected hash plus current verifier-ready classification, including workflow availability, under the same CAS-protected state read. An rk-side second export alone still leaves a race.

2. **MAJOR — The prover seam silently erases declared proof dependencies, so later acceptance can certify a different proof graph from the one produced.** The prover is explicitly asked for `depends` ([driver-prompts.ts:127](/home/tobiasosborne/Projects/rk/src/drive/driver-prompts.ts:127)), and rk preserves it during structural parsing ([driver-prove-node.ts:53](/home/tobiasosborne/Projects/rk/src/drive/driver-prove-node.ts:53)). The af seam then deliberately drops it and records only statement/inference ([driver-af.ts:135](/home/tobiasosborne/Projects/rk/src/drive/driver-af.ts:135), [driver-af.ts:148](/home/tobiasosborne/Projects/rk/src/drive/driver-af.ts:148)). Verifier prompts substitute a node’s children for its dependencies ([driver-live.ts:198](/home/tobiasosborne/Projects/rk/src/drive/driver-live.ts:198)), while af’s export explicitly omits actual dependencies ([export-graph-v1.md:54](/home/tobiasosborne/Projects/vibefeld/docs/export-graph-v1.md:54)).

   Example: the prover returns child B with `depends: [A]`; af records B as independent, and B’s verifier receives no A dependency. If accepted, the parent can subsequently validate against a provenance graph different from the prover output.

   **Fix:** extend af’s bulk-refine input/service and export to record actual dependencies and validation dependencies, then supply those exact records to the verifier and include them in the apply-time input fingerprint. Until that lands, reject any non-empty `depends` and stop requesting the field; never silently erase it.

3. **MAJOR — “Validated root” survived the refactor, but “challenged/blocked root never converges” did not.** The predicate is still only `epistemicState === "validated"` ([driver-run.ts:56](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:56), [driver-run.ts:70](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:70)), and an empty prover/verifier frontier therefore returns `converged` for any validated root ([driver-run.ts:103](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:103)). af permits a challenge on any existing node and adding it does not change that node’s epistemic state ([verdicts_apply.go:254](/home/tobiasosborne/Projects/vibefeld/internal/service/verdicts_apply.go:254), [apply.go:319](/home/tobiasosborne/Projects/vibefeld/internal/state/apply.go:319)). Its job classifiers exclude validated nodes regardless of open challenges, and exclude blocked nodes ([prover.go:55](/home/tobiasosborne/Projects/vibefeld/internal/jobs/prover.go:55), [verifier.go:50](/home/tobiasosborne/Projects/vibefeld/internal/jobs/verifier.go:50)). Consequently, a validated root with a later blocking challenge—or a validated-but-blocked root—has an empty frontier and is reported converged.

   **Fix:** export an authoritative af convergence/closure flag computed from validated state, workflow state, open blocking challenges, and child/dependency closure, and require that flag. Alternatively, raising a blocking challenge against a validated node must atomically reopen/unvalidate it; rk must still reject claimed/blocked roots.

## FOLLOW-UPS

1. **Direct prover-to-verdict isolation passes.** `proveOneNode` requires `role === "prover"`, discards top-level verdict/outcome shapes, and only calls `recordProof` ([driver-prove-node.ts:78](/home/tobiasosborne/Projects/rk/src/drive/driver-prove-node.ts:78), [driver-prove-node.ts:84](/home/tobiasosborne/Projects/rk/src/drive/driver-prove-node.ts:84), [driver-prove-node.ts:92](/home/tobiasosborne/Projects/rk/src/drive/driver-prove-node.ts:92)). The acceptance path independently requires `role === "verifier"` exactly ([driver-verify-node.ts:52](/home/tobiasosborne/Projects/rk/src/drive/driver-verify-node.ts:52)). At the rk boundary, that role equality is equivalent to blocker 3’s guard, and the structural separation is stronger because the prover module has no bind/apply path. The af `--role` flag itself is not an equivalent kernel guard, as covered by landing-blocker 1.

2. **Successful prover records defeat the stuck/retry guards; add an actual churn cap.** Every successful record resets `roundsWithoutProgress`, while attempts increase only for skips or non-accept outcomes ([driver-run.ts:124](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:124), [driver-run.ts:134](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:134), [driver-run.ts:188](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:188)). A verifier can challenge successive leaves and a prover can keep extending the chain; each structural write counts as progress without any epistemic advancement. The campaign-token cap is not the only terminator: live runs also have turn/node valves ([verify-live.ts:157](/home/tobiasosborne/Projects/rk/src/cli/verify-live.ts:157)), the driver has `maxRounds: 50` ([driver-types.ts:29](/home/tobiasosborne/Projects/rk/src/drive/driver-types.ts:29)), and ballooning aborts ([driver-run.ts:97](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:97)). Nevertheless, the existing retry cap does not count successful refinements, so it can burn the generic cap on one spinning branch. Count proof records, repeated challenge/refinement cycles, and net tree growth per node; abort with a distinct churn-cap reason when no epistemic state advances.

   None of those terminators reports success: max rounds returns `aborted` ([driver-run.ts:197](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:197)), and live safety-valve exits return code 4 ([verify-live.ts:257](/home/tobiasosborne/Projects/rk/src/cli/verify-live.ts:257)). Churn alone cannot succeed, apart from the challenged-validated-root defect in landing-blocker 3.

3. **The live challenge→prover→verifier hand-off currently cannot work.** `recordProofRefine` claims and refines but never releases the claim ([driver-af.ts:142](/home/tobiasosborne/Projects/rk/src/drive/driver-af.ts:142)); `RefineNodeBulk` returns after appending child events, also without release ([proof.go:1774](/home/tobiasosborne/Projects/vibefeld/internal/service/proof.go:1774)). It also does not resolve or supersede the open challenge. af consequently continues to classify the parent as prover work—possibly while claimed—and never verifier-ready. Make proof recording an atomic refine + challenge disposition + release operation, or explicitly perform those transitions with recoverable failure semantics. A “recorded proof” should count as progress only when that transition succeeds.

4. **Budget parity holds for dispatched run-turns, but not for session creation.** Prover and verifier both receive pre-dispatch `checkBudget`, and both add `spentTokens` regardless of rejection/discard ([driver-run.ts:126](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:126), [driver-run.ts:132](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:132), [driver-run.ts:148](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:148), [driver-run.ts:152](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:152)). That matches Lane G for `runTurn`.

   However, Claude session creation is a real model call whose returned usage is discarded ([backend-claude.ts:103](/home/tobiasosborne/Projects/rk/src/drive/backend-claude.ts:103)), and the verifier session is created before the loop’s first budget check ([verify-live.ts:151](/home/tobiasosborne/Projects/rk/src/cli/verify-live.ts:151)). This contradicts the CLI’s claim that session creation is included in the cap ([verify-live-budget.ts:12](/home/tobiasosborne/Projects/rk/src/cli/verify-live-budget.ts:12)). Prover usage records also incorrectly use the verifier session ID ([driver-prove-node.ts:75](/home/tobiasosborne/Projects/rk/src/drive/driver-prove-node.ts:75)). Propagate, pre-authorize, log, and accrue session-creation usage for both roles.

5. **Schema verdict: acceptable additive v1 evolution, not a versioning violation.** Both flags are optional `omitempty` booleans ([graph.go:83](/home/tobiasosborne/Projects/vibefeld/internal/export/graph.go:83)), and the documented v1 contract explicitly permits additive optional fields ([export-graph-v1.md:60](/home/tobiasosborne/Projects/vibefeld/docs/export-graph-v1.md:60)). rk’s structural parsers ignore unknown fields and explicitly opt into the new flags ([driver-af.ts:61](/home/tobiasosborne/Projects/rk/src/drive/driver-af.ts:61)). A schema bump would be inappropriate here.

   Compatibility validation is weaker than claimed, though: the live parser does not check `schema_version` at all, and the graph validator only requires a non-empty version ([driver-af.ts:61](/home/tobiasosborne/Projects/rk/src/drive/driver-af.ts:61), [validate-af.ts:54](/home/tobiasosborne/Projects/rk/src/graph/validate-af.ts:54)). Require version `"1"` and a capability/version preflight so an older af—where both absent flags look like “nothing ready”—fails loudly instead of as `root-unvalidated`.

6. **Verifier apply core: semantically preserved, but the blanket “byte-unchanged” claim is false.** The exact verifier-role guard, content-hash binding, cross-vendor decision, fresh-hash comparison, and one-item/non-batch apply remain intact after extraction ([driver-verify-node.ts:57](/home/tobiasosborne/Projects/rk/src/drive/driver-verify-node.ts:57), [driver-verify-node.ts:62](/home/tobiasosborne/Projects/rk/src/drive/driver-verify-node.ts:62), [driver-verify-node.ts:72](/home/tobiasosborne/Projects/rk/src/drive/driver-verify-node.ts:72), [driver-run.ts:161](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:161), [driver-run.ts:177](/home/tobiasosborne/Projects/rk/src/drive/driver-run.ts:177)). For verifier-only rounds, the prior apply decisions are preserved. End-to-end admissibility is not unchanged because prover mutations now occur before verifier dispatch and current role-readiness is not rechecked; that is landing-blocker 1.
